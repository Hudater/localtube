# Architecture

## Module map

```
core-model       → plain Kotlin data classes (Source, Channel, Playlist, Video). No Android dependency.
core-metadata    → parses yt-dlp .info.json into core-model-adjacent types. No Android dependency.
core-filesystem  → LOCAL/SMB/NFS file access abstraction. Android-dependent (SAF), no Room/UI.
core-data        → Room DB, repositories, scan engine, WorkManager worker. Depends on all of the above.
core-player      → Media3 ExoPlayer setup + custom SMB/local DataSource. Depends on core-model, core-filesystem.
app              → Compose UI, ViewModels, navigation, DI wiring, credential storage.
```

### Why this split (portability goal)

The person building this wants to reuse pieces in a future iOS or web
client without rewriting from scratch. Reusability per module, roughly
most → least:

- **core-model**: fully reusable as-is anywhere Kotlin runs (KMP shared
  module, Ktor backend, whatever).
- **core-metadata**: fully reusable as-is in a Kotlin backend; the parsing
  logic has zero Android dependency on purpose.
- **core-filesystem**: the *interface* (`SourceFileSystem`) is a good
  contract to reimplement against on a server (no SAF constraints there,
  full raw socket access), but the concrete LOCAL/SMB implementations here
  are Android-specific and won't port directly.
- **core-data**: the Room-based implementation won't port (Room is
  Android-only), but the *repository interfaces* (`SourceRepository`,
  `LibraryRepository`) are the contract a web backend's equivalent classes
  should match, so the ViewModel-facing shape doesn't need to change if
  the backing implementation ever does.
- **core-player**: Android/Media3-specific, not reusable outside Android.
- **app**: Compose UI, not reusable outside Android (obviously).

## Key decisions and why

### Downloader-agnostic by design

The app does not assume YTDLnis specifically. It only reads the yt-dlp
`.info.json` sidecar convention (see `core-metadata`), which YTDLnis,
Pinchflat, and plain yt-dlp all produce. If a different downloader is
used later, only `core-metadata` needs a second `MetadataParser`
implementation — nothing else changes.

### No cross-platform framework

Flutter, KMP, React Native, and Wails were all considered and rejected
for *this app* specifically — not because they're bad tools, but because
this app's core technical challenges (SMB socket streaming, a custom
Media3 `DataSource`, `MediaMetadataRetriever` frame extraction) are all
native-API-heavy. A cross-platform layer would need platform-channel
bridging to Kotlin for all of them anyway, adding a translation layer
without removing the native code. Native Kotlin was the lower-friction
choice for a single-maintainer personal project.

(Separately: learning Flutter/Dart for career reasons — Zerodha uses
Flutter — is a good idea, just better served by a less native-heavy
practice project than this one.)

### Manual DI, no Hilt/Dagger

`di/AppContainer.kt` is a single hand-written container with lazy
properties. Chosen deliberately over Hilt/Dagger because this is a
single-maintainer app — annotation-processor DI earns its keep on larger
teams/codebases, not here. Revisit only if the container genuinely
becomes unwieldy (dozens of entries) or a second contributor joins.

### Scan diffing strategy

`ScanEngine` diffs by filename + file size + last-modified time, NOT by
hashing file contents. Hashing a multi-GB video file over SMB on every
scan would be far too slow. The tradeoff: a file replaced with different
content but identical size+mtime (rare, but possible if someone
manually touches files) won't be detected as changed. Acceptable for
this use case.

### Home feed ordering

Deliberately `ORDER BY RANDOM()` (see `VideoDao.observeFeed`), not
chronological — the goal is a YouTube-like "variety" feel on the home
feed, not a most-recent-first list. This was an explicit design choice,
not an oversight.

### Videos vs Playlists tab split

A channel page's "Videos" tab shows only standalone videos
(`playlist_id IS NULL`); playlist content only appears under "Playlists"
— never duplicated into the flat Videos list. This mirrors YouTube's own
channel page behavior and was explicitly decided over the flat-list
alternative.

### Channel dedup across sources

Channels are deduplicated by `channel_id` (yt-dlp's stable ID), never by
display name — two unrelated channels can share a display name, but IDs
don't collide. This is why `ChannelEntity`'s primary key is the string
ID itself, not an autogenerated Room row ID.

### Multi-select source selector

The source selector (top bar dropdown) supports selecting any
combination of sources, not just "one source" or "all sources". An empty
selection set is treated as "All" (see `SelectionState.isAllSelected()`)
rather than "nothing selected" — this was a deliberate UX choice so
there's no confusing empty-feed state after deselecting everything.

### Credential storage

SMB usernames/passwords are stored in `EncryptedSharedPreferences`
(Android Keystore-backed), NOT in the Room database. `SourceEntity` only
stores the username (for display, e.g. showing "connected as X" in
settings) — never the password. Rationale: Room's SQLite file is
trivially readable on a rooted device or in an unencrypted backup;
Keystore-backed storage is a meaningfully higher bar for a personal app
holding home-server credentials.

### Hidden sources

Hidden is a plain boolean column (`SourceEntity.hidden`), filtered with
`WHERE hidden = 0` everywhere. This is visual declutter only — explicitly
NOT encryption or access control. Don't ever repurpose this flag as a
security boundary.

## Custom media URI scheme (`localtube://`)

ExoPlayer's `MediaItem` and Coil's image loader both need a `Uri`. Since
video/thumbnail files don't have real URLs (they're local SAF documents
or SMB paths), both playback and thumbnail loading encode a source ID +
relative path into a `localtube://<sourceId>/<relativePath>` URI (see
`core-player`'s `LocalTubeMediaItems`). Neither DataSource nor Coil's
`ThumbnailFetcher` ever puts credentials in this URI — SMB auth is
resolved via `SmbCredentialProvider`/`EncryptedSmbCredentialStore`
lookups keyed by source ID, not carried in the URI itself.

## Known gaps / open items

These are real gaps discovered while scaffolding, not just "future
ideas" — read this list before assuming a feature is done.

1. **Verify the actual info.json schema.** `core-metadata/YtDlpInfoJson.kt`
   is built from yt-dlp's documented field names, but has NOT been
   validated against a real `.info.json` file produced by your specific
   YTDLnis/Pinchflat setup. Before relying on this in production: grab
   one real `.info.json` from your download folder, run it through
   `YtDlpMetadataParserTest`-style assertions (or just eyeball the field
   names), and fix `YtDlpInfoJson.kt` if anything's off. This file is
   intentionally the single place to fix it.

2. **NFS is not implemented.** Only `SourceType.LOCAL` and `SourceType.SMB`
   have `SourceFileSystem` implementations wired into `AppContainer`.
   The requirements doc listed NFS as a secondary priority behind SMB —
   this reflects that; add `NfsSourceFileSystem` and register it in
   `AppContainer.fileSystemsByType` when needed.

3. **Channel avatar thumbnails are never populated.** `ScanEngine` always
   writes `ChannelEntity.thumbnailPath = null`. yt-dlp's info.json doesn't
   reliably include a channel-level avatar image — sourcing one (e.g.
   from a channel's own thumbnail file if one exists in the source, or
   leaving it as an initials-based placeholder in the UI) is unresolved.
   Currently the avatar strip will show a blank colored circle for every
   channel.

4. **Playlist thumbnails are never populated.** Same issue —
   `PlaylistEntity.thumbnailPath` is always null from `ScanEngine`. The
   requirements doc's intent was "defaults to first video's thumbnail" —
   this needs to be resolved either at scan time (look up the first
   video by `playlist_index` and copy its thumbnail path) or at read time
   in `LibraryRepository`/the UI layer. Not yet done either way.

5. **Per-source scan failure isn't surfaced to the UI.** `ScanWorker`
   catches exceptions per-source (so one unreachable SMB share doesn't
   block scanning others) but doesn't currently report *which* source
   failed anywhere the UI can show it. The requirements doc calls for an
   "unavailable" indicator on a source's content — the plumbing for that
   (e.g. a `lastScanError` column on `SourceEntity`) doesn't exist yet.

6. **No WorkInfo observation for manual refresh.** `HomeViewModel.onRefresh()`
   fires `ScanScheduler.scanNow()` and clears its own spinner after a
   fixed 1.5s delay, rather than actually observing the enqueued work's
   completion via `WorkManager.getWorkInfoByIdFlow`. Works fine visually
   for a quick scan; will feel wrong if a scan legitimately takes longer
   than 1.5s (e.g. a large SMB share on first scan).

7. **Video/Channel/Playlist objects don't survive process death mid-navigation.**
   `MainActivity` keeps an in-memory `videoLookup` map to hand `Video`
   objects to the player screen without making them `Parcelable`. This
   works for normal in-app navigation but not if Android kills the
   process while the user is on the player screen and later restores it
   — the `player/{videoId}` route does fall back to a DB lookup by ID in
   that case (see the `LaunchedEffect` in `MainActivity`), so it won't
   crash, but it's worth knowing this fallback path is the less-tested
   one.

8. **No tests beyond `core-metadata`.** The yt-dlp parser has real unit
   tests. `ScanEngine`'s diffing logic, the repositories, and the UI have
   none yet — worth adding before this grows much further, especially
   around `ScanEngine`'s file-grouping logic, which is the trickiest pure
   logic in the codebase.

9. **`minifyEnabled` is off for release builds.** Fine for a personal
   single-device app (smaller attack surface for reverse engineering
   doesn't matter here), but means release APK size and startup time
   aren't optimized. Revisit only if that becomes a real annoyance.

## Extension points (where to add things later)

- **New downloader format**: add a `MetadataParser` implementation in
  `core-metadata`, don't touch anything else.
- **NFS support**: add `NfsSourceFileSystem` in `core-filesystem`,
  register it in `AppContainer.fileSystemsByType`.
- **A second UI surface (e.g. tablet layout)**: everything under `ui/`
  reads from the same ViewModels — new Composables can be added
  alongside the existing ones without touching `core-*`.
- **Web backend reusing metadata/scan logic**: `core-metadata` ports
  directly; `core-data`'s repository *interfaces* are the shape to match,
  not the Room-backed implementations.
